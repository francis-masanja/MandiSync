How It Works

The browser talks to Next.js, which in turn talks to Prisma, and the ESP32 nodes send data to the API. Both the gate and scale readings end up in the same booking record.

Omer · Owner Backend · Area

In one minute

Two paths meet in one place. The browser path goes from the React pages through Next.js and Prisma to the database. The device path goes from the ESP32 nodes to the API. Both end up in the same booking record.

What this part covers

When the browser loads the React pages, the server components pull data from the shared data layer, while the client components call the v1 API routes. Before any protected page or API call goes through, middleware checks the session and the user's role.

The gate node posts an RFID tag to the gate-verify endpoint and receives a gate-open decision. Meanwhile, the scale node sends gross and tare weights to the weighbridge endpoint. On the server side the readings are stored, the net weight is calculated, the booking gets updated, and a telemetry log is written. Finally, the queue ledger reads the same booking table.

Key terms

Route handler A server function under app/api that handles an HTTP request.
Middleware Code that runs before a request reaches a page or route.
HMAC A keyed hash used to prove that a device request is genuine.
LittleFS A small file system on the ESP32 used to buffer readings when Wi-Fi is down.

Picture this

How the two paths join: the browser reads and writes through Next.js and Prisma, while the gate and scale send their readings to the API. Both paths land in the same booking record, so the gate, scale and queue screens stay consistent.

The three requests to remember

Gate

gate-verify

The gate node posts an RFID tag and receives a gate-open decision.

Scale

weighbridge

The scale node sends gross and tare weights, so the server can calculate net weight.

Offline

batch-sync

When Wi-Fi is down, LittleFS buffers readings on the ESP32 until they can sync.

What to remember

  • The browser path goes through Next.js and Prisma to the database.
  • Middleware checks the session and the user's role before protected pages or API calls.
  • Gate and scale readings are stored, net weight is calculated, the booking is updated, and a telemetry log is written.
  • The queue ledger reads the same booking table, so everyone sees the same record.

Your part

Omer owns the backend. That means the backend APIs, the booking and telemetry services, and validation of the incoming requests. The goal is one clean booking record that the gate, scale and queue all share.
