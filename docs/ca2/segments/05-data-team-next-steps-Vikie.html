Segment 5

Data, Team and Next Steps

We’ve got six tables that cover everything: users, mandis, slots, bookings, telemetry and tasks. The prototype is functional, but we still need to harden it for production.

Owner: Vikie Area: Database

In one minute

Six tables hold the whole story. Users book slots, mandis own those slots, bookings collect the weights, and tasks keep follow-up work moving. Prisma keeps the schema and migrations tidy, and SQLite or Turso stores the data.

The data model is the backbone of the project. It keeps the farmer, gate, weighbridge and queue views looking at the same records instead of separate spreadsheets.

What this part covers

The database is relational. One user can make many bookings, and each mandi contains multiple slots and bookings. A slot is tied to a single booking, while a booking can have lots of telemetry readings. Tasks link a user—and occasionally a booking—to any follow-up work. Prisma handles the schema and migrations, and the actual data lives in SQLite or Turso.

We divided the tasks according to technical area—hardware, frontend, middleware, backend, and database. Everyone also takes charge of a report section and an HTML study guide. We’re upfront about what still needs to be done: automated tests, database-backed users, device HMAC verification, a public landing page, and a real deployment pipeline.

Key terms

Primary key A column that uniquely identifies each row.
Foreign key A column that points to a row in another table.
Migration A versioned SQL change that updates the database schema.
HMAC verification The server checks that a device request was signed with the correct secret.

Picture this

The six tables

Table What it stores Key links
User Login identity and role: farmer, operator or admin. One user has many bookings and many tasks.
Mandi Market location, GPS point and daily capacity. One mandi has many slots and many bookings.
Slot One arrival window, with a start and end time. Belongs to one mandi; a slot can be booked only once.
Booking The farmer’s delivery request and its progress. One user, one mandi, one unique slot; many telemetry readings and tasks.
Telemetry Gate and weighbridge readings, live or buffered. Each reading belongs to one booking.
Task Follow-up work for staff, with an optional due date. Belongs to one user; may also point to a booking.

A unique email per user and a unique slot per booking stop two bookings from claiming the same window.

What to remember

  • The project has six main tables: User, Mandi, Slot, Booking, Telemetry and Task.
  • The links are clear: a user makes many bookings, a mandi has many slots and bookings, a slot belongs to one booking, and a booking has many telemetry readings.
  • Finished: the relational schema, the Prisma schema and migrations, and the main booking, gate, weighbridge and queue flows as a working prototype.
  • Still planned: automated tests, database-backed users, device HMAC verification, a public landing page and a real deployment pipeline.

Your part

Vikie · Database

Vikie owns the Prisma schema, the migrations, the relationships and data integrity. That means defining the six tables, writing the versioned schema changes, preparing seed data, and checking the constraints the API depends on—like the unique email on User and the unique slot on Booking.

If a query returns the wrong shape or a link between tables breaks, the database owner is the first person to check the schema and the migration history.

Baby recap
